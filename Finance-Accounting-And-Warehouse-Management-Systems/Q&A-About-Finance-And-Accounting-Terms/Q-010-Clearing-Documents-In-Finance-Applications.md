إليك شرح شامل لمفهوم **وثائق التسوية (Clearing Documents)** في الأنظمة المالية المؤسسية، مع التركيز على الفروقات الجوهرية بين SAP وOracle.

---

### 1. مفهوم وثيقة التسوية (Clearing Document)

**الوصف بالعربية:**
وثيقة التسوية هي **قيد محاسبي خاص يُنشأ تلقائيًا أو يدويًا لإغلاق عنصر مفتوح (Open Item)** وربطه بعنصر مقابل (دفعة، إشعار دائن/مدين، أو قيد تسوية آخر). هذه الوثيقة ليست مجرد تسجيل مالي، بل هي **"ختم إلكتروني"** يؤكد أن الالتزام قد تم الوفاء به أو تسويته محاسبيًا.

#### الخصائص المميزة لوثيقة التسوية:
-   **لا تؤثر على الرصيد الإجمالي للحساب:** مجموع المدين والدائن في وثيقة التسوية يساوي صفرًا دائمًا.
-   **تغير حالة العنصر:** تحول العناصر المرتبطة من "مفتوح" (Open) إلى "مُسوّى" (Cleared).
-   **تحمل مرجعية مزدوجة:** تربط بين الوثيقة الأصلية (الفاتورة/الدفعة) ووثيقة التسوية نفسها.
-   **تحتوي على بيانات تسوية فريدة:** مثل تاريخ التسوية، مبلغ الفرق المسحوب، وسبب التسوية.

### 2. وثائق التسوية في SAP S/4HANA

في SAP، وثيقة التسوية هي **كيان تقني مستقل** له خصائص محددة:

#### الهيكل التقني:
-   **Document Type:** عادةً `DZ` (تسوية عملاء)، `KZ` (تسوية موردين)، `DA` (تسوية بنك)، أو أنواع مخصصة.
-   **Clearing Date (AUGDT):** تاريخ فعالية التسوية (قد يختلف عن تاريخ الترحيل).
-   **Clearing Document Number (AUGBL):** رقم الوثيقة الذي يظهر في جميع العناصر المُسواة المرتبطة بها.
-   **Zero-Balance Principle:** يجب أن يكون صافي الأسطر المُسواة = 0 (أو ضمن حدود التحمل المسموحة).

#### أنواع وثائق التسوية في SAP:
| النوع | المعاملة | الوصف |
| :--- | :--- | :--- |
| **Normal Clearing** | F-03, FBL5N | تسوية عادية تربط فاتورة بدفعة متطابقة تمامًا. |
| **Residual Item** | F-03 مع خيار Residual | تُغلق الفاتورة الأصلية بالكامل وتنشئ عنصرًا مفتوحًا جديدًا بقيمة المتبقي. وثيقة التسوية تربط الأصلي بالعنصر الجديد. |
| **Difference Posting** | F-03 مع Difference | تُغلق الفاتورة والدفعة وتنشئ قيدًا إضافيًا للفرق (مصروف/إيراد). وثيقة التسوية تشمل ثلاثة عناصر. |
| **Cross-Company Clearing** | F-03 عبر شركات | تسوية عناصر مفتوحة بين شركات مختلفة داخل المجموعة. تنشئ وثائق تسوية متعددة مترابطة. |

#### مثال عملي في SAP:
```
فاتورة أصلية: Doc #1900000045 | مدين عميل | 1,000€ | Open
دفعة واردة: Doc #1900000078 | دائن عميل | 1,000€ | Open

→ عملية F-03 → وثيقة تسوية DZ #1900000090
   - تربط Doc #45 و Doc #78
   - AUGDT = 15.11.2024
   - كلا العنصرين يصبحان Cleared مع الإشارة إلى AUGBL = 1900000090
```

### 3. وثائق التسوية في Oracle Fusion Cloud ERP

في Oracle، المفهوم مختلف جوهريًا؛ **لا توجد وثيقة تسوية مستقلة بالمعنى السابي**، بل التسوية هي **عملية تطبيق (Application)** تُحدث حالة العناصر:

#### النموذج المفاهيمي:
-   **Receipt Application / Credit Memo Application:** هي العملية المكافئة للتسوية.
-   **No Separate Clearing Document:** لا يُنشأ رقم وثيقة جديد. بدلاً من ذلك، يتم تحديث حقول `Applied_To`, `Application_Date`, `Application_Reference` في الجدول الفرعي.
-   **Accounting Entries Generated:** عند تشغيل Create Accounting، تُنشأ قيود محاسبية تعكس التطبيق، لكنها تحمل نفس رقم الوثيقة الأصلية (Receipt/Credit Memo).

#### آليات التسوية في Oracle:
| الآلية | الوصف | الفرق عن SAP |
| :--- | :--- | :--- |
| **Standard Application** | تطبيق إيصال على فاتورة مباشرة. | لا يوجد clearing doc number؛ الرابط هو Application ID داخلي. |
| **On-Account Credit** | الاحتفاظ بالإيصال كرصيد متاح دون تطبيقه. | مكافئ لعنصر مفتوح دائن في SAP، لكن بدون وثيقة تسوية. |
| **Write-Off Application** | شطب فرق صغير كجزء من عملية التطبيق. | يُنشأ قيد write-off منفصل، لكن التطبيق نفسه لا يولد وثيقة تسوية. |
| **Reversal of Application** | إلغاء تطبيق سابق. | يعيد العناصر لحالة Unapplied دون إنشاء وثيقة تسوية عكسية. |

#### مثال عملي في Oracle:
```
فاتورة: INV-2024-00123 | Amount: 1,000$ | Status: Open
إيصال: RCP-2024-00456 | Amount: 1,000$ | Status: Unapplied

→ Apply Receipt → Application ID: APP-78901
   - Invoice Status → Applied
   - Receipt Status → Applied
   - No new document number created
   - Create Accounting generates JE linked to RCP-2024-00456
```

### 4. مقارنة جوهرية: SAP vs Oracle

| جانب المقارنة | SAP S/4HANA | Oracle Fusion Cloud |
| :--- | :--- | :--- |
| **الكيان التقني** | وثيقة مستقلة برقم فريد (AUGBL) | عملية تطبيق (Application) بدون رقم وثيقة منفصل |
| **الأثر على الأستاذ العام** | قيد ترحيل مستقل بنوع وثيقة خاص | قيد محاسبي مشتق من الوثيقة الأصلية عند Create Accounting |
| **التتبع والتدقيق** | سهل عبر AUGBL؛ يمكن عرض كل العناصر المُسواة بوثيقة واحدة | يتطلب الاستعلام عبر Application Tables أو Reconciliation Reports |
| **المرونة في التسوية الجزئية** | Residual Item ينشئ عنصرًا جديدًا بوثيقة تسوية واضحة | Partial Application يحدث الحالة فقط؛ المتبقي يبقى في نفس العنصر |
| **التسوية عبر الشركات** | وثائق تسوية متعددة مترابطة تلقائيًا | Intercompany Receivables/Payables مع تطبيقات منفصلة وتسوية لاحقة |
| **عرض العناصر المُسواة** | FBL5N/FBL1N مع خيار Cleared Items | Receivables/Payables Registers مع فلتر Applied |
| **التعامل مع فروق التسوية** | Difference Posting ضمن وثيقة التسوية نفسها | Write-Off أو Adjustment كعملية منفصلة مرتبطة بالتطبيق |

### 5. اعتبارات حرجة للممارسين

1.  **في SAP:** فهم أنواع وثائق التسوية ضروري لتصميم تقارير التدقيق. رقم AUGBL هو المفتاح الذهبي لتتبع دورة حياة أي عنصر مفتوح.
2.  **في Oracle:** لا تبحث عن "وثيقة تسوية"؛ ركز على فهم **Application Lifecycle** وكيفية استخراج بيانات التطبيق للتقارير والتدقيق.
3.  **الهجرة بين النظامين:** عند الانتقال من SAP إلى Oracle (أو العكس)، فإن تحويل بيانات العناصر المُسواة هو أحد أكبر التحديات بسبب الاختلاف الجوهري في نموذج البيانات.
4.  **التسوية الآلية:** في كلا النظامين، جودة وثائق/عمليات التسوية تعتمد كليًا على جودة البيانات المرجعية في العناصر المفتوحة الأصلية.
5.  **الامتثال والضرائب:** في بعض الدول، تتطلب السلطات الضريبية وثائق تسوية رسمية. في Oracle، قد تحتاج إلى تخصيص تقارير لتلبية هذا المتطلب نظرًا لعدم وجود وثيقة مستقلة.

هل ترغب في التفاصيل التقنية لاستخراج تقارير وثائق التسوية في أحد النظامين، أو في تصميم استراتيجية هجرة تأخذ في الاعتبار هذا الاختلاف الجوهري؟
